# Odysseus / Context Reduction And Compaction Review

## Epistemic Status

This is a review hypothesis, not an observed claim about Odysseus.

The working suspicion is that hidden or automatic context reduction can become one of the highest-risk drift boundaries in human-AI collaboration. The purpose of this leaf is to define what to inspect in Odysseus before claiming whether the risk exists there.

## Parent Link

This leaf continues `001.trace.md`, which framed the broader Odysseus provenance/replayability offer around agent and tool execution, runtime decisions, model/provider surfacing, and later auditability without relying on chat history, memory, or guesswork.

## Problem Statement

When a human builds coherence with an LLM over a long working thread, implicit or automatic compaction can break shared understanding.

The issue is not only that tokens are reduced. The issue is that the reduction may silently decide:

- which goals still govern
- which constraints remain active
- which decisions were landed
- which uncertainties were preserved
- which tool results count as evidence
- which context was dropped
- which assumptions were smuggled forward as fact

If the human does not see or participate in that reduction, the human and LLM can continue under different mental models while both believe continuity was preserved.

## Review Hypothesis

A provenance-safe runtime should treat context reduction as an observable reduction event rather than a hidden optimization.

At minimum, a reviewer should be able to determine:

- whether reduction occurred
- what triggered it
- what was retained
- what was dropped or compressed
- what uncertainty survived
- whether the human had a chance to review, correct, accept, or reject the reduction
- whether the next agent turn can be reconstructed from the reduction artifact

## Preferred Direction

The preferred Tiinex-aligned strategy is not to auto-compact the primary human-facing work thread without user visibility.

A safer direction is:

- primary conversation coherence remains human-visible and human-governed
- reduction is invoked on demand or exposed as a visible boundary when forced by context pressure
- the reduction draft is consolidated with the human before it becomes authoritative carry-forward context
- reduction artifacts preserve retained claims, dropped claims, open uncertainty, and next-step state
- follow-up work continues from an explicit accepted reduction instead of an implicit runtime summary

## Alternative Architecture Direction

A runtime can reduce drift by separating user coherence from codebase/tool noise.

A strong user relation would be:

- the human chats in one stable platform or primary thread
- the platform delegates bounded work to an IDE or agent surface
- the IDE-side agent reads codebase/tool context and performs noisy execution
- the IDE-side agent returns compact, evidence-bearing results to the primary thread
- the primary thread preserves decisions, constraints, and human intent without absorbing every file read, tool trace, or recovery turn

This is related to the common `main thread + runSubAgent` pattern, but the subagent boundary must return enough metadata and durable work context to be useful.

## Concern With Thin Subagent Returns

A subagent call is not sufficient by itself if it only returns a shallow answer.

For replayability, a useful subagent result should expose at least:

- input mode and parent task
- selected model/provider and selection rationale when available
- declared, allowed, blocked, observed, and executed tools
- files or external sources materially used
- evidence anchors for major conclusions
- changes attempted or made
- stop reason and completion claim
- unresolved work and validation limits
- carry-forward summary that the parent can accept or reject
- path or identifier for durable evidence, trace, or log material

Without this, `runSubAgent` can reduce context pollution but still fail as a continuity mechanism.

## Odysseus Review Questions

When evaluating Odysseus, inspect whether the runtime exposes:

- context-window pressure or reduction triggers
- automatic summarization, compaction, memory writes, or session reduction behavior
- user-visible controls for summarization or context carry-forward
- agent memory update paths and whether they are reviewable
- boundaries between chat history, memory, tool results, documents, and agent state
- whether long-running agent tasks preserve intermediate rationale or only final output
- whether tool execution loops create durable evidence or disappear into transient logs
- whether model/provider routing changes are visible after the fact
- whether the user can reconstruct why a later answer behaved differently than an earlier one

## Candidate Validation Pass

A small first pass should avoid broad runtime claims.

Suggested validation target:

1. Find the code paths or docs that handle conversation state, memory, session persistence, agent execution, and summarization.
2. Map where context can be reduced, summarized, written to memory, or carried into a new agent step.
3. Classify each reduction path as one of:
   - human-visible and reviewable
   - human-visible but not reviewable
   - implicit but logged
   - implicit and hard to reconstruct
   - not yet found
4. Identify one concrete PR, issue, or runtime path where this matters.
5. Return findings with clear separation between static review, local runtime observation, and unvalidated hypothesis.

## Non-Goals

This leaf does not claim that Odysseus currently performs unsafe automatic compaction.

This leaf does not require Odysseus to adopt Tiinex formats.

This leaf does not require a specific architecture before the current runtime behavior is understood.

This leaf does not ask for broad maintainer access or roadmap control.

## Risks

- Overstating the issue before observing Odysseus behavior.
- Confusing model context limits with product-level memory or session compaction.
- Treating all summarization as bad rather than distinguishing visible, reviewable reduction from hidden reduction.
- Asking for too much metadata before knowing which runtime paths are actually critical.
- Collapsing user-facing chat coherence, IDE-side execution, memory, and evidence into one vague "context" concept.

## Expected Output

The intended output of this sub-topic is a bounded review checklist or issue note that can answer:

- where context reduction can happen in Odysseus
- whether the user can see or influence it
- whether a later reviewer can reconstruct it
- what minimal metadata would make it safer
- which parts were validated and which remain assumptions
