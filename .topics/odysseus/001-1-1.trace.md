# Odysseus / Minimum Observable Reduction Surface

This leaf reduces the broader context-reduction review topic into one practical review surface that does not require Odysseus to adopt Tiinex formats.

## Source Context

This reduction continues `001-1.trace.md`, which framed hidden or automatic context reduction as a possible human-LLM drift boundary for Odysseus review.

The fuller source context included:

- the broader provenance/replayability offer from `001.trace.md`
- the `001-1.trace.md` hypothesis that context reduction should be treated as an observable event rather than a hidden optimization
- the distinction between full Tiinex lineage and a smaller non-invasive runtime improvement
- the new `tiinex.reduction.v1` schema as the proper artifact role for observable carry-forward reduction

## Carry-Forward State

The smallest useful claim to carry forward is:

> Any runtime that reduces, compacts, summarizes, prunes, or carries forward conversational or agent context should expose enough information for the user or reviewer to tell what survived, what was lost or degraded, what remains uncertain, and what assumptions now govern the next step.

This does not require Tiinex adoption.

A minimum observable reduction surface should expose:

- Reduction Occurred: whether context was reduced, compacted, summarized, pruned, or carried forward
- Trigger: why reduction happened, such as context pressure, session resume, memory write, model switch, agent handoff, or explicit user action
- Source Scope: which conversation, session, task, tool-output range, memory slice, or runtime state was reduced
- Carry-Forward State: the goals, constraints, decisions, open questions, evidence anchors, and next actions that now govern continuation
- Retained Signals: material considered preserved for future work
- Dropped Signals: material omitted or intentionally not carried forward
- Degraded Signals: material compressed in a way that may lose fidelity
- Uncertainty: unresolved, ambiguous, or unverified state that must not be treated as settled fact
- Human Review State: whether the reduction was hidden, shown, accepted, corrected, rejected, or still unreviewed
- Recoverability: whether the fuller source remains reachable through transcript, log, evidence artifact, runtime export, or other durable reference
- Runtime Linkage: whether later agent/model turns can be tied back to the reduction that shaped them

The strongest minimum behavior is not "store everything in Tiinex." It is:

> If the runtime compresses shared working context, the compression must become visible enough that drift can be detected.

## Loss And Uncertainty

This leaf intentionally drops broader implementation questions from `001-1.trace.md`, including full architecture proposals, subagent metadata completeness, and long-term transcript storage strategy.

This leaf does not claim that Odysseus currently performs hidden or unsafe reduction.

This leaf does not claim that every transcript, memory item, or runtime log should become a core Tiinex schema artifact.

This leaf does not require Odysseus to keep the full conversation in a repository, although Tiinex may prefer that for its own recoverability standard.

Unresolved questions:

- whether Odysseus currently has explicit summarization, compaction, pruning, or memory-write flows
- whether those flows are user-visible
- whether their outputs are durable enough to support later review
- whether a minimal visible summary would be enough for Odysseus users or whether a stronger artifact boundary would be needed
- whether runtime logs, database state, memory stores, or agent traces are the best initial validation target

## Validation

Status: proposed review surface, not an observed runtime finding.

Validation needed before making claims about Odysseus:

1. Inspect Odysseus code and documentation for conversation state, session persistence, memory, summarization, context-window handling, and agent handoff paths.
2. Identify whether any path reduces or carries context forward.
3. Classify each path as:
   - visible and reviewable
   - visible but not reviewable
   - hidden but logged
   - hidden and hard to reconstruct
   - not found
4. For each found path, check whether the minimum observable fields above can be reconstructed.
5. Report static-code findings separately from runtime-observed findings.
6. Preserve evidence links or excerpts for any concrete claim.

## Review Checklist

Use this checklist for a bounded Odysseus pass:

- Where can conversation or agent context be reduced?
- What triggers reduction?
- Is the user told that reduction happened?
- Can the user inspect the reduced carry-forward state?
- Can the user correct or reject the carry-forward state before it governs future behavior?
- Are retained, dropped, degraded, and uncertain signals distinguishable?
- Does the runtime preserve a pointer to the fuller source context?
- Can later behavior be traced back to the reduction that shaped it?
- Are memory writes treated as reviewable carry-forward state or as hidden background mutation?
- Are tool results and evidence anchors preserved when context is summarized?
- Are model/provider changes visible when they affect carry-forward behavior?
- Is there a safe fallback when reduction cannot be validated?

## Non-Goals

- Do not demand Tiinex format adoption as a first step.
- Do not require a dedicated transcript or memory schema for this review.
- Do not treat all summarization as bad.
- Do not claim Odysseus is unsafe before observing concrete behavior.
- Do not broaden the review into general maintainer work.
