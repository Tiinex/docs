# Software Ideas Branch

This branch is for ideas whose likely next serious receivers are software
builders, product owners, engineering-adjacent operators, or teams working on
digital systems.

## Current Read

The role of this branch is to hold software-oriented idea continuity without
forcing every child into the same product category.

It should be broad enough to support tools, internal systems, user-facing
software, and workflow-supporting digital products.

## Design Direction

For this branch, continuation should usually prefer:

- problem-first software ideas over technology-for-its-own-sake
- preserving likely receiver and ownership shape early
- leaving architecture choices, stack choices, and exact build scope to later
  children
- using support repositories for grounding only when a narrower child truly
  depends on them

## Good Child Shapes

Likely useful child shapes include:

- developer or operator tools
- workflow software
- knowledge and coordination systems
- automation support surfaces
- user-facing products with a clear task or problem boundary

## Multi-Root Grounding Note

This branch is the most likely place where later children may need support from
other workspace repositories for examples, runtime constraints, feedback, or
implementation evidence.

That grounding should be attached in narrower children when needed, not merged
loosely into this root.

## Next Artifacts

- continue narrower software lines only when one concrete receiver, problem,
  or product boundary becomes clear
- attach repo-specific evidence later when a child line needs real technical
  grounding
